# ベンチマーク

このページでは、リポジトリにある 2 つのベンチマークバイナリと、それぞれが何を測るか、そしてそれらが実際に出した数値をまとめます。ここに載っている数値はすべてそのどちらかが出したものであり、推定値の場合は本文にそう書いてあります。これらの数値をどう使うかは [パフォーマンス](./performance.md) を参照してください。

## 2 つのベンチマークバイナリ

どちらも `tests/benchmark/` にあり、他のテストと一緒にビルドされ、`benchmark` ラベルで CTest に登録されます。テストケースには `DISABLED_` の接頭辞が付いているため、通常のテスト実行では飛ばされます。実行に数分かかるうえ、負荷のかかった共有マシンで測った時間には意味がないためです。

`similarity_benchmark` は、サーバーも TCP も経由せずに検索パイプラインの構成要素を直接測ります。測るのは 8 つです。ベクトルストアのデフラグ処理の再構築時間、事前計算したノルムを使うブルートフォースのコサインスキャン、それに続く top-k の選択、リザーバサンプリング、アイテム検索とベクトル検索という 2 つのエンドツーエンドの入口、ヒットとミスそれぞれのクエリキャッシュの参照レイテンシ、そして排他ロック下でのクエリキャッシュの変更コストです。

`ann_recall_benchmark` は、近似索引が使えるかどうかを決める唯一の指標、すなわち再現率とレイテンシのトレードオフを測ります。ANN の構造はどれも、答えを悪くすればいくらでも速くできます。したがって `hnsw` や `ivf` のレイテンシだけを見ても何も分かりません。このバイナリはトレードオフを決めるつまみ、HNSW なら `hnsw_ef_search`、IVF なら `ivf_nprobe` を振り、曲線上のすべての点で再現率をレイテンシと並べて出力します。正解は同じベクトル群を同じ距離関数で全走査したものなので、バイナリがビルドできる環境ならどこでも再現でき、取得すべきデータセットもありません。

## 実行方法

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel

./build/bin/similarity_benchmark --gtest_also_run_disabled_tests
./build/bin/ann_recall_benchmark --gtest_also_run_disabled_tests
```

単一の計測だけを実行する場合は次のようにします。

```bash
./build/bin/similarity_benchmark --gtest_also_run_disabled_tests \
  --gtest_filter="*SearchByIdVectors*"

./build/bin/ann_recall_benchmark --gtest_also_run_disabled_tests \
  --gtest_filter="*HnswRecallVsEfSearch*"
```

ビルドは `Release` で行ってください。素の `make` はビルドタイプを選ばず最適化レベルも選ばないため、以下のどの数値も数倍悪くなり、何とも比較できなくなります。

`ann_recall_benchmark` は表示だけでなく検証もします。曲線を出力したうえで、測定した再現率をバイナリに記録された下限と突き合わせるため、グラフや分割の品質を落とす変更は、公開された曲線を黙って誤らせるのではなく実行の失敗として現れます。次元とコーパスの組み合わせごとに 5 万ベクトルの索引を構築し、すべてのクエリについて全走査で正解を求めるため、自動実行には組み込まれていません。

## 計測環境

以下の数値は次の環境で得られたものです。

- **ハードウェア**: Apple M5 Max (arm64)、128 GB のユニファイドメモリ
- **SIMD**: NEON。実行時に選択
- **ビルド**: `Release`、`-O3 -march=native`、Apple Clang
- **設定**: 既定値。`distance_metric: cosine`、`sample_size: 10000`、`index_type: flat`
- **方法**: データを投入したストアに対する 15 回の中央値、次元 128、`top_k` は 10

Apple Silicon は一般的なサーバーのメモリ構成よりメモリ帯域が広く、NEON は 128 ビット幅で AVX2 の 256 ビットより狭くなっています。したがって x86_64 サーバーでの絶対的なレイテンシは両方向にずれ、そちらは計測していません。コーパスサイズに対するスケールの傾向のほうが移植可能です。

## 検索レイテンシ

`SimilarityEngine` を通したエンドツーエンド、次元 128、`top_k` は 10、コサインです。

| ベクトル数 | アイテム ID による検索 | クエリベクトルによる検索 |
|---|---|---|
| 1,000 | 0.010 ms | 0.010 ms |
| 10,000 | 0.092 ms | 0.092 ms |
| 50,000 | 0.59 ms | 0.58 ms |
| 100,000 | 0.90 ms | 0.91 ms |

これらは既定の `sample_size` である 10,000 で実行しており、サンプリングはコーパスがその 2 倍を超えると働きます。したがって上 2 行は全走査ですが、50,000 行と 100,000 行はまずサンプルを選びます。そのサンプルを選ぶリザーバ処理はコーパス全体を走査するため、距離計算の量は増えなくてもコストはコーパスサイズとともに増えます。2 つの入口が 1 パーセント以内で一致するのは想定どおりで、両者はクエリベクトルを引くか渡されるかしか違いません。

割り算すると、100,000 ベクトルの数値は 1 スレッドあたり毎秒およそ 1,100 クエリにあたります。

## 構成要素のコスト

100,000 ベクトル、次元 128 で個別に計測したものです。

| 構成要素 | 中央値 |
|---|---|
| 事前計算ノルムによるコーパス全体のブルートフォースコサインスキャン | 0.73 ms |
| 100,000 件の候補に対する部分ソートでの top-k 選択 | 0.06 ms |

全走査では距離スキャンが支配的なコストです。これは上のエンドツーエンドの行の内訳ではありません。あちらはこの規模では全走査せずサンプリングするからです。ここに挙げたのは `sample_size: 0` が選ぶ全走査の経路のコストです。

## デフラグ

ベクトルを削除すると墓標が残ります。墓標がスロットの 4 分の 1 を超えるとストアは自身を再構築し、その入れ替えのために排他ロックを取ります。ベクトルの 25% を削除した状態、次元 128 での結果は次のとおりです。

| ベクトル数 | 再構築 |
|---|---|
| 1,000 | 0.03 ms |
| 10,000 | 0.27 ms |
| 50,000 | 1.49 ms |
| 100,000 | 3.07 ms |

## クエリキャッシュのレイテンシ

100 件、1,000 件、10,000 件、50,000 件のエントリを保持したキャッシュに対する参照レイテンシです。

| 操作 | 中央値 |
|---|---|
| ミス。キーが存在しない | 0.042 µs、およそ 42 ns |
| ヒット。キーが存在し、エントリを展開して返す | 0.21 µs、およそ 208 ns |

100,000 ベクトルでのエンドツーエンドの 0.90 ms と比べると、ヒットのコストはコールドなクエリのおよそ 4,000 分の 1 です。参照のコストは保持エントリ数が増えても目に見えて増えないので、キャッシュを大きくしても遅くはなりません。

変更のベンチマークが測るのは、読み手ではなく書き手にとってのキャッシュのコストです。すでにデータの入ったキャッシュへ 1 件を挿入する場合と、あるアイテムを参照するエントリを無効化する場合を、保持エントリ数 1,000 件、5,000 件、20,000 件で測ります。どちらも排他ロックを保持します。この計測の数値はここには載せていません。自分のハードウェアでの値を得るには実行してください。得られた値の使い方は [パフォーマンス](./performance.md) にあります。

## 近似索引の再現率

同じコーパスの全走査を正解とした `top_k` 10 での再現率です。5 万ベクトル、コサイン、1 点あたり 200 クエリ、次元は 128 と 768 です。コーパスの形は 2 種類を測ります。一様なコーパスは独立にランダムな方向を引いたもので、高次元ではほぼ直交するため近傍がほとんど区別できず、グラフ型でも分割型でも近似索引にとって最悪の条件です。クラスタ化したコーパスは 200 個の潜在的な重心の周りに点を引いたもので、実際の埋め込みが持つ形です。

クラスタ化したコーパスでベンチマークが検証する再現率の下限は次のとおりです。

| 索引 | つまみ | Recall@10 の下限 |
|---|---|---|
| `hnsw` | `hnsw_ef_search` 10 | 0.97 |
| `hnsw` | `hnsw_ef_search` 32 | 0.99 |
| `hnsw` | `hnsw_ef_search` 64 | 0.99 |
| `ivf` | `ivf_nprobe` 1 | 0.90 |
| `ivf` | `ivf_nprobe` 4 | 0.98 |
| `ivf` | `ivf_nprobe` 8 | 0.98 |

HNSW は `hnsw_m` 16、`hnsw_ef_construction` 200 で、IVF は `ivf_nlist` 256 で計測しています。実際の掃引はこの表より広く、`hnsw_ef_search` は 10 から 512、`ivf_nprobe` は 1 から 128 まで動かし、各点で再現率、レイテンシの中央値と 99 パーセンタイル、全走査に対する速度比を出力します。

一様なコーパスは意図的に検証の対象外です。ほぼ直交するベクトルは近似検索が割に合わなくなる領域であり、そこでの結論は特定の数値に届くことではなく、割に合わないということだからです。

3 つ目の計測は、索引を単体で使うのではなく、サーバーが実際に通る経路で IVF を駆動します。ベクトルは 1 件ずつ届き、`ivf_train_threshold` を超えるとサンプルに対する学習が非同期に走り、バッファされたベクトルはバックグラウンドの処理で転置リストへ公開されます。速度比は同じコーパスを同じエンジンで `index_type: flat` にした場合に対して報告されます。実際に選択の対象になるのがそちらだからです。同じ再現率の下限を適用するため、公開された曲線はベンチマークが自前で作った配置ではなくサーバーが生み出すものと突き合わされます。

## 計測していないこと

読者が求めがちで、ここのどのベンチマークも出さないため、このページのどこにも書いていないものが 3 つあります。

- **操作単位の SIMD の実行時間**。スカラー、NEON、AVX2 の距離カーネルには正しさのテストはありますが、時間を測る仕組みはありません。得られている SIMD の数値は上のスキャン全体のコストだけで、しかも NEON でのものです。
- **サンプリング経路の再現率**。`sample_size` は精度と速度を交換しますが、再現率のベンチマークが測るのはサンプルではなく ANN 索引です。自分のコーパスでの値を知るには、同じクエリを `sample_size: 0` と検討中の値の両方で実行し、結果集合を比べてください。
- **10 万ベクトルを超える挙動と、スナップショットの保存時間およびファイルサイズ**。これより大きなコーパスを読み込むベンチマークも、スナップショットを計時するベンチマークもありません。どちらも自分のデータで測る方法は [パフォーマンス](./performance.md) にあります。
