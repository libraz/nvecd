# クエリキャッシュ

nvecd は類似検索の結果をメモリに保持し、同じクエリの再実行を避けます。このページでは、何がどんなキーで入るのか、保存するかどうかを決めるコスト閾値、圧縮、追い出しと期限切れの規則、書き込みがどうキャッシュを無効化するか、`CACHE` コマンドの操作面、そして統計の読み方を扱います。

キャッシュは既定で有効、容量は 32 MB です。ここで挙げる設定キーは、値の範囲とあわせて [configuration.md](./configuration.md) に記載されています。

## キャッシュされるもの

エンジンが返した `SIM` と `SIMV` の結果リストがそのまま、つまり ID とスコアが、`min_score` を適用する前の形で入ります。それ以外は入りません。書き込み、`INFO`、`CONFIG`、スナップショット系のコマンドがキャッシュを参照することはありません。

各エントリは 3 つの検索種別のいずれかに分類され、種別ごとに独立したポリシーを持ちます。

| 検索種別 | クエリ | 有効 | TTL |
|---|---|---|---|
| アイテム検索 | `filter=` なしの `SIM` | する | `cache.ttl_seconds` |
| ベクトル検索 | `filter=` なしの `SIMV` | しない | — |
| 絞り込み検索 | `filter=` 付きのいずれか | する | 60 秒 |

ベクトル検索はキャッシュされません。`SIMV` はクエリベクトルをその場で渡すので、まったく同じベクトルが再送されることは稀であり、キャッシュしてもヒットを得られないままメモリを使うからです。ただし `filter=` を伴う `SIMV` は絞り込み検索であり、こちらはキャッシュされます。これらのポリシーは設定キーではなくコードに埋め込まれています。

## キャッシュキー

キーは、クエリとそれが答えた時点の状態から組み立てた文字列の MD5 ダイジェストです。`SIM` の場合は次のようになります。

```text
SIM:<id>:<top_k>:<mode>:a<adaptive>:g<co_occurrence_gen>:v<vector_gen>:m<metadata_gen>:d<dataset_gen>[:f<filter>]
```

`SIMV` ではアイテム ID の位置にクエリベクトルの生バイト列の MD5 ダイジェストが入り、共起世代とモードはありません。

```text
SIMV:<vector_digest>:<top_k>:v<vector_gen>:m<metadata_gen>:d<dataset_gen>[:f<filter>]
```

`<adaptive>` は `on`、`off`、またはクエリが指定しなかった場合の `default` です。つまり、設定の既定値に任せたクエリと、同じ値を明示したクエリは別のキーになります。

結果を変えうるものはすべてキーに入っているので、ミスの予測はどの要素が違うかを確かめる作業になります。

- `top_k` が違えば別のキーです。10 件の要求が 20 件のキャッシュを流用することはなく、5 件の要求がキャッシュ済み 20 件の先頭 5 件を再利用することもありません。
- `using=` のモードが違えば別のキーです。
- フィルタ式は呼び出し側が書いたとおりの文字列としてキーに入ります。`filter=a=1,b=2` と `filter=b=2,a=1` は、同じ絞り込みでも別のキーです。
- 4 つの世代カウンタがキーに入ります。`co_occurrence_gen` は共起スコアを変えるイベントと減衰サイクルごとに、`vector_gen` は `VECSET` と `VECDEL` ごとに、`metadata_gen` は `METASET` とメタデータを伴う書き込みごとに、`dataset_gen` は `DUMP LOAD` と起動時の復旧で進みます。

`min_score` は意図的に含まれていません。キャッシュが返した結果に対して後から適用されるので、1 つのキャッシュ結果があらゆる下限に対して使われます。`min_score=0.5` のクエリと `min_score=0.9` の同じクエリは、同じエントリにヒットします。

## コスト閾値

結果が保存されるのは、検索に `cache.min_query_cost_ms`（既定 10.0）以上かかった場合だけです。計測の対象はエンジンの呼び出しそのもので、パースや応答の整形は含みません。

閾値があるのは、安いクエリはキャッシュしても得るものがなく、メモリだけは使うからです。数千本のベクトルに対する `flat` 検索は 1 ミリ秒を大きく下回るので既定値では決して保存されません。大きなコーパスに対して選択性の高いフィルタを付けた `hnsw` 検索なら、容易に超えます。閾値を 0 まで下げるとすべてがキャッシュされます。調査には便利ですが、大して節約にならないエントリでメモリ上限を埋めることになります。

閾値の判定はキャッシュを使わなかった場合のコストに対して行われるので、一度も閾値を超えないクエリは毎回実行され、キャッシュはそれを恒久的なミスとして報告します。これは不具合ではなく意図した結果です。

## 圧縮

結果は 1 行あたり 260 バイト固定、つまり 256 バイトの ID バッファと 4 バイトのスコアに直列化され、`cache.compression_enabled`（既定 true）が有効なら LZ4 で圧縮してから保存されます。

圧縮が引き合うのは、この固定幅のレイアウトのおかげです。実際のアイテム ID は 256 バイトよりはるかに短いので、各レコードの大半はゼロ埋めであり、LZ4 がほぼ完全に取り除きます。節約はエントリあたりの行数とともに大きくなるので、エントリが大きいところでちょうど最大になります。圧縮を切ると直列化した形のまま保存され、そのメモリと引き換えにヒットごとの伸長が省けます。

256 バイト以上の、あるいは NUL バイトを含むアイテム ID は切り詰めずに保存できないため、誤った内容をキャッシュするのではなく結果セット全体を拒否します。そうしたクエリは単にキャッシュされません。

## 追い出し、メモリ、TTL

キャッシュは `cache.max_memory_mb`（既定 32）で上限を持ちます。計上の対象は圧縮済みのペイロード、キー、コンテナのオーバーヘッド、無効化用の索引で、再計算ではなく増分で維持されるため、エントリが出入りしても正確なままです。

挿入が上限を超えそうなときは、最も長く使われていない側から収まるまで追い出し、1 回のパスで少なくとも `cache.eviction_batch_size` 件（既定 10）を落とします。まとめて追い出すのは、満杯になったあと挿入のたびに追い出しが走るのを避けるためです。上限そのものより大きい結果セットは、そもそも受け付けられません。

`cache.ttl_seconds`（既定 3600）はエントリを経過時間で期限切れにします。エントリは挿入時に有効だった TTL から算出した絶対期限を保持し、参照時には現在のグローバル TTL に対しても経過時間を再判定するので、実行中に TTL を下げれば既に載っているエントリにも効きます。TTL が 0 なら期限切れは無効です。

期限切れの処理は遅延式です。参照したときに期限切れと分かって取り除かれるのであって、バックグラウンドの掃除は走りません。二度と参照されない期限切れエントリは、LRU の圧力で追い出されるまでメモリを保持し続けます。

## 無効化

2 つの仕組みが組み合わさって働きます。どちらも全体クリアではありません。

キーに含まれる世代カウンタが、古いエントリを到達不能にします。`VECSET` は `vector_gen` を進め、これは `SIM` と `SIMV` のすべてのキーに現れるので、それ以降に発行されたクエリが、それ以前に計算されたエントリへハッシュすることはありません。正しさを保証しているのはこちらです。新規のアイテムについても同様で、既存のエントリはそれを参照していないため、アイテム単位の仕組みだけでは取りこぼします。

逆引き索引はメモリを回収します。各エントリは自分が関わるアイテム ID、すなわちクエリの ID と結果の ID を、1 エントリあたり 50 件まで記録します。そのいずれかへの書き込みは、参照しているエントリを古びるのを待たずに即座に消します。`EVENT`、`VECSET`、`VECDEL` はいずれもこの方式で、変更されたアイテムの ID についてのみ無効化します。

選択的な無効化があるからこそ、キャッシュはイベントストリームが流れ続ける環境で使いものになります。レコメンドのワークロードはイベントを絶えず書き込むので、イベントのたびにキャッシュを空にしていたら、ヒットするまで生き残るものが何もありません。触れられたアイテムに言及するエントリだけを消せば、残りのワーキングセットは無傷で残ります。

より広く効く書き込みが 2 つあります。`METASET` と、メタデータを伴う `VECSET` はキャッシュを丸ごとクリアします。メタデータの変更は絞り込みを伴う任意のクエリが返すアイテムを変えますし、メタデータは逆引き索引が追跡している対象ではないので、消すべきエントリをより狭く特定できないからです。

挿入する側にも対応する防護があります。結果が保存されるのは、キャッシュが参照時と同じ公開インスタンスのままで、有効なままで、かつ 4 つの世代カウンタが参照時に取得した値をすべて保っている場合だけです。クエリの実行中に書き込みが入った場合は、すでに動いてしまった状態に対して計算されたリストをキャッシュするのではなく、そのクエリの結果を捨てます。

## CACHE コマンド

```bash
CACHE STATS
CACHE CLEAR
CACHE ENABLE
CACHE DISABLE
```

`CACHE CLEAR` はキャッシュを空にして `OK CACHE_CLEARED` を返します。`CACHE ENABLE` と `CACHE DISABLE` はそれぞれ `OK CACHE_ENABLED` と `OK CACHE_DISABLED` を返します。どちらも実行時変数 `cache.enabled` を設定するので、`SET cache.enabled true` とコマンドは同じことをします。

無効化はクエリハンドラからキャッシュを外し、参照も挿入も止めますが、保持している内容は捨てません。再び有効にすれば同じエントリが再び使われます。ただし TTL と世代カウンタには従うので、その間に何か書き込まれていればカウンタは進んでいます。メモリを空けたいのであれば明示的にクリアしてください。

`cache.min_query_cost_ms` と `cache.ttl_seconds` も `SET` で実行中に変更できます。

同じ操作は HTTP 側にもあり、`GET /cache/stats`、`POST /cache/clear`、`POST /cache/enable`、`POST /cache/disable` として公開されています。[http-api.md](./http-api.md) を参照してください。

## 統計の読み方

`CACHE STATS` は `OK CACHE_STATS` に続けて統計 1 件につき 1 行の `field: value` を返し、`END` で終わります。

```text
OK CACHE_STATS
cache_enabled: true
cache_entries: 1284
cache_memory_bytes: 6291456
current_memory_mb: 6.00
min_query_cost_ms: 10.00
ttl_seconds: 3600
compression_enabled: true
eviction_batch_size: 10
total_queries: 48210
cache_hits: 31877
cache_misses: 16333
cache_misses_invalidated: 0
cache_misses_not_found: 16333
cache_hit_rate: 0.6612
evictions: 903
ttl_expirations: 1160
avg_hit_latency_ms: 0.041
avg_miss_latency_ms: 0.002
total_time_saved_ms: 402118.55
END
```

`GET /cache/stats` は同じ数値を JSON で返します。フィールド名は `enabled`、`total_queries`、`cache_hits`、`cache_misses`、`cache_misses_invalidated`、`cache_misses_not_found`、`hit_rate`、`current_entries`、`current_memory_bytes`、`current_memory_mb`、`min_query_cost_ms`、`ttl_seconds`、`compression_enabled`、`eviction_batch_size`、`evictions`、`avg_hit_latency_ms`、`avg_miss_latency_ms`、`time_saved_ms` です。

キャッシュがメモリに見合っているかは、1 つの比較で判断できます。`total_time_saved_ms` はヒットが肩代わりしたクエリの元のコストの総和で、これがキャッシュで得られた分です。これを `cache_memory_bytes` と比べてください。32 MB を保持して 1 時間あたり数分のクエリ時間を節約しているなら見合っています。数ミリ秒なら見合っていません。

`cache_misses_not_found` は、キーがそもそも存在しなかったことを意味します。本当に新しいクエリか、世代の要素が進んでしまったクエリです。not-found が多くヒット率が低い状態は、たいていクエリの傾向に反復が乏しいか、書き込みがクエリの反復より速く世代カウンタを進めていることを示します。どちらもキャッシュにメモリを足しても解決しません。`cache_misses_invalidated` は、参照時にすでに陳腐化の印が付いていたエントリを数えますが、書き込みの経路は印を付けるのではなくエントリを消すため、この値は 0 のままで、ミスはすべて `cache_misses_not_found` に入ります。

`evictions` が伸び続ける一方で `cache_hit_rate` が低いままなら、ワーキングセットが `cache.max_memory_mb` に収まっておらず、2 回目にヒットする前にエントリが落とされています。上限を引き上げて効果があるのはこの場合です。

`ttl_expirations` が伸びてヒット率が低いなら、再利用される前にエントリが古びています。`cache.ttl_seconds` を上げるべきですが、古い結果が今も正しいと言えるだけ元のデータが安定していることを確かめてからにしてください。

`avg_hit_latency_ms` は参照と伸長を含みます。これを `avg_miss_latency_ms` と比べても有用ではありません。ミスの計測は参照が失敗した時点までで、そのあとに続く検索は含まないからです。意味があるのは、`avg_hit_latency_ms` を、保存されるクエリが超えなければならないコストである `cache.min_query_cost_ms` と比べることです。
