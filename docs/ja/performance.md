# パフォーマンス

このページはチューニングの手引きです。どの設定が何を変え、それぞれ何を代償にするのか、そして変更が効いたかどうかをサーバー自身の出力からどう判断するのかを扱います。実測値は [ベンチマーク](./benchmarks.md) にあり、ここでは繰り返しません。

## 検索モードの選択

`SIM` と `SIMV` は `using=` でどの信号が問い合わせに答えるかを選びます。3 つのモードは読む構造が違うため、コストも違います。

| モード | 読む対象 | コスト |
|---|---|---|
| `using=vectors` | ベクトルストアのみ | 距離のスキャン、または ANN 索引の参照 |
| `using=events` | 共起索引のみ | 対象アイテムの近傍集合の参照 |
| `using=fusion` | 両方を配分して合成 | 上の 2 つの合計に、合成の分を加えたもの |

共起検索のコストは対象アイテムが蓄えた近傍の数で決まり、コーパスサイズには依存しないため、コーパスが大きくなっても安いままです。ベクトル検索はスキャンするベクトル数に比例します。統合検索は両方のコストを払います。

問いに答えられるもっとも安いモードを選んでください。内容の類似はベクトルだけで足り、「このアイテムと一緒に現れるもの」は共起だけで足ります。結果が両方を反映しなければならず、追加のレイテンシに見合う場合に統合検索を使います。配分が何をしているかは [統合検索](./fusion.md) を参照してください。

`SIMV` はアイテム ID ではなくクエリベクトルを取り、`using=` オプションを一切受け付けません。近傍を引くためのアイテムがないため、常にベクトル検索です。

## イベント側の構造のサイジング

イベント側が保持する量は 3 つの設定で決まり、いずれもメモリと品質の交換です。

```yaml
events:
  ctx_buffer_size: 50
  max_contexts: 0
  max_neighbors_per_item: 0
  min_support: 0.0
```

`ctx_buffer_size` はコンテキストあたりのリングバッファの長さ、つまり 1 つのコンテキストが覚えている直近のイベント数です。届いたイベントはバッファに残っているイベントすべてと共起するため、この長さが関連付けの届く範囲を決め、`EVENT` 1 件のコストもこれに比例して増えます。短いバッファはセッションを、長いバッファは履歴をモデル化します。

`max_contexts` は常駐するコンテキスト数の上限で、最後に動きのあった時刻が古いものから削ります。0 のままだと無制限で、訪問者ごとに新しいコンテキストを作るワークロードでは際限なく増えます。コンテキストが閉じた集合から来ないなら必ず設定してください。

`max_neighbors_per_item` は 1 アイテムが蓄える近傍集合の上限です。共起索引はマップのマップなので、これがその幅を決めます。上限がないと、人気のあるアイテムはこれまで一緒に現れたすべてのものへの辺を蓄え、メモリも共起検索のコストもその数に比例して増えます。

`min_support` はスコアが閾値を下回る辺を落とし、一度しか観測されていない関連付けの裾を取り除きます。件数ではなくスコアで刈るため減衰と組み合わさります。`decay_alpha` が 1 未満なら、補強されなくなった辺はやがて閾値を割り込んで落ちます。

人気が裾の重い分布を持つワークロードでは、`max_neighbors_per_item` と `min_support` の少なくとも一方を設定してください。両方とも無制限のままにすることが、イベント側のメモリに上限がなくなる典型的な原因です。

## 索引タイプの選択

`similarity.index_type` はベクトル検索に答える構造を選びます。

```yaml
similarity:
  index_type: "flat"
  sample_size: 10000
```

`flat` はすべてのベクトルを走査して厳密な top-k を返します。既定値であり、構築の手順も学習も要らず、走査がレイテンシの予算に収まる規模のコーパスならこれが正解です。コストはコーパスサイズと次元の両方に比例します。

`hnsw` は探索可能なグラフを構築します。再現率はクエリ時の探索幅である `hnsw_ef_search` で調整し、大きくするほどグラフを広く探索して再現率が上がり、レイテンシも増えます。`hnsw_m` と `hnsw_ef_construction` はグラフそのものを決めて構築時に効くため、変更には再構築が要ります。`hnsw_max_elements` は起動時に容量を予約するもので、0 のままならグラフは必要に応じて伸びます。

`ivf` はコーパスを `ivf_nlist` 個のセルに分割し、クエリごとに `ivf_nprobe` 個を探索します。再現率は `ivf_nprobe` で調整します。この索引は学習しないと何も答えられません。`ivf_train_threshold` 件のベクトルが届いた時点で学習が非同期に始まり、その間に書き込まれたベクトルはバッファされてバックグラウンドの処理で転置リストへ公開されます。両方が終わるまでクエリはスキャンにフォールバックするため、コールドスタートや一括投入の直後の IVF サーバーは定常状態のレイテンシではありません。

つまみの値は、出したいレイテンシではなく必要な再現率から決めてください。[ベンチマークの再現率の下限](./benchmarks.md#近似索引の再現率) がクラスタ化したデータでの両方の曲線の形を示しています。再現率は最初に急に上がってから頭打ちになるため、最後のわずかな再現率は最初の分より不釣り合いに多くのレイテンシを要します。設定は自分のベクトルで確認してください。再現率はコーパスがどれだけクラスタ化しているかに依存し、ほぼ直交するベクトルのコーパスではどの近似索引も割に合いません。

`sample_size` は走査経路に効く独立した近似です。コーパスがその 2 倍を超えると、クエリはコーパス全体ではなくランダムなサンプルにスコアを付けます。距離計算の量は抑えられますが、サンプルを引くリザーバ処理は依然として全ベクトルを走査するため、抑えられるのはスキャンのコストであってクエリのコストが一定になるわけではありません。厳密な答えが要るなら 0 にします。

## クエリキャッシュのチューニング

```yaml
cache:
  enabled: true
  max_memory_mb: 32
  min_query_cost_ms: 10.0
  ttl_seconds: 3600
  compression_enabled: true
  eviction_batch_size: 10
```

キャッシュが何かをするかどうかを決めるのが `min_query_cost_ms` です。結果が保存されるのは、それを作るのに少なくともこの時間がかかった場合だけなので、クエリが閾値を大きく下回るコーパスでは何も保存されず、キャッシュはメモリと参照時間を消費しながら何も返しません。`max_memory_mb` を上げる前に、実際に観測されるクエリのレイテンシと閾値を比べてください。

`max_memory_mb` は常駐エントリの上限です。上限に達すると 1 件ずつではなく `eviction_batch_size` 件をまとめて追い出し、排他ロック下の処理を均します。`ttl_seconds` は経過時間でエントリを失効させ、0 にすると失効しなくなるため、エントリが出ていく経路は無効化と追い出しだけになります。`compression_enabled` は結果を LZ4 に通し、参照時間をわずかに犠牲にして同じ予算でより多くのエントリを収めます。

### キャッシュ統計の読み方

```bash
nvecd-cli CACHE STATS
```

応答は `OK CACHE_STATS` で始まり、カウンタを 1 行ずつ並べ、`END` で終わります。

```text
OK CACHE_STATS
cache_enabled: true
cache_entries: 2450
cache_memory_bytes: 13056921
current_memory_mb: 12.45
min_query_cost_ms: 10.00
ttl_seconds: 3600
compression_enabled: true
eviction_batch_size: 10
total_queries: 10000
cache_hits: 8500
cache_misses: 1500
cache_misses_invalidated: 320
cache_misses_not_found: 1180
cache_hit_rate: 0.8500
evictions: 320
ttl_expirations: 12
avg_hit_latency_ms: 0.000
avg_miss_latency_ms: 0.920
total_time_saved_ms: 7820.00
END
```

キャッシュがメモリに見合っているかは、4 つの読み方で判断できます。

`total_time_saved_ms` と `current_memory_mb` の対比が直接の答えです。それだけの常駐メモリと引き換えに、キャッシュが実際に削ったレイテンシを表します。予算いっぱいを保持しながらほとんど削れていないキャッシュは、見合っていません。

`cache_hit_rate` だけを見ると誤ります。`total_queries` が `cache_hits + cache_misses` をほとんど超えない状態で率が低いなら、ワークロードに繰り返しが少ないというだけで、何をしても変わりません。`evictions` が増えている状態で率が低いなら、稼働中の集合に対して予算が足りていません。

`cache_misses_invalidated` と `cache_misses_not_found` の対比が、2 種類のミスを切り分けます。未発見のミスは、これまで来たことのないクエリです。無効化によるミスは、いったんキャッシュされた答えが、元のアイテムが変わったために捨てられたものです。この割合が高いなら、同じアイテムに対して書き込みが読み込みを上回っており、キャッシュのメモリを増やしても解決しません。

`avg_hit_latency_ms` と `avg_miss_latency_ms` の対比が、キャッシュで削れている割合です。両者が近いなら、クエリはすでに十分速く、見るべきは予算ではなく `min_query_cost_ms` です。

`CACHE CLEAR` はキャッシュを空にし、`CACHE ENABLE` と `CACHE DISABLE` は再起動なしに有効と無効を切り替えるため、稼働中のワークロードで A/B の計測ができます。

## ベクトルの次元

`vectors.default_dimension` はストアに対して固定です。これは 3 つのものを同時に増やします。ベクトル 1 件が占めるメモリ、距離計算 1 回の仕事量、そしてベクトル上に構築される ANN 索引のサイズです。

走査経路は次元に比例するため、次元を半分にすればスキャンのコストもおおむね半分になります。実測値があるのは次元 128 だけで、[ベンチマーク](./benchmarks.md#検索レイテンシ) にあります。他の次元はこのスケールに従いますが、計測はしていません。埋め込みモデルの側で選べるなら、次元が小さいほうがコストのあらゆる面で安く、品質の差は nvecd ではなくモデルの性質です。

`vectors.distance_metric` は `cosine`、`dot`、`l2` から選びます。コサインは正規化を行うため、ストアはベクトルごとにノルムを事前計算して保持でき、候補あたりの計算を内積だけに減らせます。

## SIMD が効いているかの確認

距離カーネルには AVX2、NEON、スカラーの実装があり、CPU が報告する機能から実行時に選ばれます。サーバーは起動時に一度、選択結果をログに出します。

```text
[info] Vector SIMD: NEON
```

値は AVX2 を持つ x86_64 では `AVX2`、64 ビット ARM では `NEON`、どちらもなければ `Scalar` です。どちらかがあるはずのマシンで `Scalar` になっている場合、原因は CPU ではなくビルドです。AVX2 のビルドは configure の時点でコンパイラが `-mavx2` を受け付けた場合にだけ作られ、その結果は CMake が configure 中のステータス行として報告します。

## メモリのサイジング

ベクトルのメモリは計測ではなく計算です。ストアは連続した行列を 1 つ、ベクトルごとにノルムを 1 つ、正規化済みフラグと削除フラグをそれぞれ 1 ビット、そしてアイテム ID の文字列とその索引エントリを保持します。

```text
bytes ≈ vectors × dimension × 4      （行列。float32）
      + vectors × 4                  （ノルム）
      + vectors × 2 / 8              （正規化済みビットと削除ビット）
      + vectors × (ID の長さ + 索引のオーバーヘッド)
```

次元が数十を超えると行列が支配的になります。次元 768 なら 100 万ベクトルで行列だけがおよそ 3 GB になり、残りは端数です。ベクトルを削除しても行列は縮みません。墓標が立つだけで、領域が戻るのはストアがデフラグしたときです。

イベントのメモリに同じような式はありません。共起索引はマップのマップで、その幅はデータ次第だからです。近傍を持つアイテムの数と、それぞれが蓄えた近傍の数の積で増え、両方の文字列キーが保存されます。これを抑えるのが `max_neighbors_per_item` です。

キャッシュのメモリは `max_memory_mb` で上限が決まり、`CACHE STATS` が正確に報告します。

合計を見積もるのではなく読んでください。`INFO` は `used_memory_bytes` を報告しますが、この値はベクトル行列、つまりベクトル数と次元と 4 の積しか数えないため、プロセス全体を過小に見積もります。HTTP のメトリクスエンドポイントは `nvecd_memory_bytes` を報告し、こちらはイベントストア、ベクトルストア、共起索引の合計で、キャッシュを含みません。どちらもアロケーターのオーバーヘッドを含まないため、マシンのサイジングはオペレーティングシステムが報告するプロセスの値に対して行い、これらは内訳の把握に使ってください。

## 監視

### INFO

```bash
nvecd-cli INFO
```

応答はセクションに分かれ、`END` で終わります。`total_commands_processed` と `failed_commands` がエラー率を、`active_connections` と `performance.max_connections` の対比が接続の余裕を、`event_commands`、`sim_commands`、`vecset_commands` が読み書きの比率を、`memory_health` がメモリ逼迫についてのサーバー自身の判断を、`cache_hit_rate` がキャッシュの代表値を、そして `id_count`、`ctx_count`、`vector_count`、`event_count` が他の数値の前提となるデータ量を示します。

### メトリクスエンドポイント

`api.http.enable` を有効にすると、サーバーは Prometheus のテキスト形式を公開します。

```bash
curl http://localhost:8080/metrics
```

公開されるのは `nvecd_uptime_seconds`、コマンド別と合計の `nvecd_commands_total`、`nvecd_memory_bytes`、`nvecd_vectors_total`、`nvecd_events_total`、`nvecd_contexts_total`、そしてキャッシュの系列である `nvecd_cache_queries_total`、`nvecd_cache_hits_total`、`nvecd_cache_misses_total`、`nvecd_cache_hit_rate`、`nvecd_cache_entries` です。

アラートを設定すべきなのは変化率です。`vecset` の `nvecd_commands_total` が伸びながら `nvecd_cache_hit_rate` が下がるなら、書き込みが読み込みによる再充填を上回っています。`nvecd_vectors_total` が横ばいのまま `nvecd_memory_bytes` が伸びるなら、増えているのはイベント側です。

### ヘルスエンドポイント

エンドポイントは 4 つあり、いずれもコマンドの計数対象外なので、プローブしてもカウンタは動きません。

| エンドポイント | 用途 |
|---|---|
| `GET /health` | タイムスタンプ付きの単純な生存確認 |
| `GET /health/live` | 生存プローブ。プロセスが動いている間は 200 |
| `GET /health/ready` | 準備プローブ。準備できていれば 200、スナップショットの読み込み中は 503 |
| `GET /health/detail` | コンポーネントごとの状態、稼働時間、イベントストア・ベクトルストア・共起索引の件数 |

ロードバランサーの下に置くべきなのは `GET /health/ready` です。スナップショットの読み込み中は `not_ready` を 503 とともに返します。まさにその間、サーバーは待ち受けてはいても有用な応答ができません。

```bash
curl -s http://localhost:8080/health/detail
```

応答には `status`、`uptime_seconds`、そして `components` オブジェクトが入ります。その中の `vector_store` はベクトル数と次元を、`event_store` はコンテキスト数とイベント数を、`co_index` は近傍を持つアイテムの数を示します。

## 遅いクエリの切り分け

コストに効く順に設定を見ていきます。

1. 起動ログの SIMD の選択結果を確認します。AVX2 か NEON のはずのところが `Scalar` なら、どの設定変更でも取り戻せないほどのコスト差です。
2. `DEBUG ON` でデバッグ出力を有効にし、同じセッションでクエリを再実行します。この設定は接続ごとなので、別の単発実行には引き継がれません。以降の `SIM` と `SIMV` の応答には、答えたモード、マイクロ秒単位のクエリ時間、検討した候補数、返した結果数を並べたブロックが付きます。候補数が結果数を大きく上回るなら、必要以上にスコアを付けています。
3. `CACHE STATS` を読みます。`total_queries` が伸びているのにヒット率がほぼ 0 なら、たいていは `min_query_cost_ms` が実際のクエリのコストより上にあり、何も保存されていません。
4. モードが問いに必要な以上の仕事をしていないか確認します。`using=vectors` で答えられる問いを統合検索で投げれば、両方の信号のコストを払います。
5. コーパスサイズと索引タイプを突き合わせます。`flat` はすべてを走査するので、コーパスがレイテンシの予算を超えて育ったのなら、それはチューニングではなく構造の答えです。

レイテンシではなくメモリが問題なら、まず `nvecd_memory_bytes` を読んでどちら側が伸びているかを見て、その側を抑えます。キャッシュなら `max_memory_mb`、イベントなら `max_neighbors_per_item` と `max_contexts`、ベクトルなら次元かコーパスサイズです。

## 複数台での運用

nvecd にはレプリケーションも、クラスタリングも、ノード間のスナップショット同期も、分散クエリもありません。2 台目のサーバーは独立した 2 台目のサーバーであり、両者を一致させるものはすべて運用者が書くことになります。

成立する方法は、スナップショットから読み取り用のレプリカを作ることだけです。

```bash
nvecd-cli DUMP SAVE replica-sync.dmp
scp /var/lib/nvecd/snapshots/replica-sync.dmp replica:/var/lib/nvecd/snapshots/
ssh replica nvecd-cli DUMP LOAD replica-sync.dmp
```

これで得られるものを正確に述べます。レプリカはスナップショットを取った時点の状態を保持します。それ以降にプライマリが受け付けた書き込みはすべて欠けており、次にコピーするまで欠けたままです。陳腐化の窓はコピーの間隔そのものであり、ワークロードがそれを許容するかどうかの判断は運用者に委ねられます。

はっきりさせておくべき帰結があります。書き込みは 1 台に集める必要があります。競合を解決する仕組みはありません。そもそもサーバー間に競合を検出できるプロトコルがないからです。`DUMP LOAD` は受け取った側の状態を置き換えるため、レプリカが自分自身の書き込みを受け付けることはできません。読み込み中は `GET /health/ready` が 503 を返すので、ロードバランサーの振り分けから外したレプリカは準備が整えば自分で戻ります。読み取り専用のトラフィックはレプリカ間で自由に分散できます。どのレプリカも完結した独立のコピーだからです。ただし、レプリカごとに少しずつ違う状態から答えが返ることをアプリケーションが許容する必要があります。

スナップショットのコストを自分のデータで測るには、リポジトリのどのベンチマークもこれを出さないため、`DUMP SAVE` の往復を計時して、できたファイルのサイズを見ます。

```bash
time nvecd-cli DUMP SAVE
ls -l /var/lib/nvecd/snapshots/
```

実際に運用する規模のデータを入れたサーバーに対して実行してください。`fork` モードでは保存を fork した子プロセスが行うため、往復時間は書き込みのコストではなく fork のコストに近く、ファイルはコマンドが返った後に現れます。保存が進行中かどうかは `DUMP STATUS` が報告します。モードの違いは [永続化](./persistence.md) を参照してください。
