# リアルタイムフィード

関与が駆動するフィードです。いま反応が集まっているものが、昨日反応を集めたものより上に来ます。このガイドでは、独立した 2 つの減衰、タイムスタンプ、スキップや非表示から得る負のシグナル、そして途切れない高頻度の書き込みを一定のメモリに収める設定を扱います。

共起の仕組みは[レコメンドのガイド](./recommendations.md)を前提にします。

## このワークロードが違うところ

カタログのレコメンドは、ゆっくり変わるデータセットに対する読み取り中心の処理です。フィードはその逆です。表示も読み飛ばしも非表示も、すべてが書き込みになります。そして検索が読む結びつきは、たいてい数分前にできたものです。ここから 2 つのことが導かれます。

新しさは後処理ではなくスコアの一部でなければなりません。「最近」の別リストを作って積を取るような仕組みがないからです。そしてメモリは到着レートではなく設定で抑えなければなりません。トラフィックの側にそれを抑える性質は何もないからです。

## 2 つの減衰は別のもの

nvecd には結びつきを薄れさせる仕組みが 2 つあり、互いに独立しています。フィードではふつう両方を使います。

**全体減衰**は `events.decay_interval_sec` 秒ごとに、共起索引のすべてのスコアへ `events.decay_alpha` を掛けます。タイマーで動き、一律に効き、個々のイベントがいつ届いたかは見ません。スコアが際限なく伸びるのを止めているのがこれです。

**時間減衰**は組ごとに、取り込みの時点で効きます。`events.temporal_cooccurrence` を有効にすると、組の寄与は 2 つのイベントそれぞれが新しいほうからどれだけ離れているかによる指数の係数を掛けられ、その差が `events.temporal_half_life_sec` 秒進むごとに半分になります。同時刻の 2 イベントは積をそのまま寄与し、半減期 1 時間の設定で 1 時間離れた 2 イベントは半分を寄与します。

この違いが効くのは、答えている問いが別だからです。全体減衰は結びつきがどれだけ古いかを見ます。時間減衰は 2 つの関与がどれだけ離れていたかを見ます。あるアイテムの直後に見られたアイテムは、同じセッションで 1 時間後に見られたアイテムより強い手がかりですが、それを表せるのは時間減衰だけです。

フィードでは、半減期を「一緒に関与したことがまだ意味を持つ幅」に合わせます。動きの速いストリームなら 1 時間から数時間です。全体減衰の間隔は、昨日の流行が目に見えて薄れる程度に短くします。

## タイムスタンプ

イベントのタイムスタンプは UNIX 秒です。`EVENT` はスコアのあとに `timestamp=<秒>` を受け取り、省略するとサーバーの時計を使います。

```bash
nvecd-cli -p 11017 EVENT u_alice ADD clip_sunset 90 timestamp=1788400000
nvecd-cli -p 11017 EVENT u_alice ADD clip_sunset 90
```

キューやログから再生するイベントでは必ず明示してください。そうすれば時間減衰は、書き込みが届いた時刻ではなく関与が起きた時刻で計算されます。

## 負のシグナル

スキップ、非表示、フォロー解除はどれも情報です。それを弱い正の値として記録すれば、グラフには弱い正の値として残り続けます。`EVENT <ctx> DEL <id>` が取り消しの形で、要求の内容によらずスコア `0` で記録されるため、それ自体は結びつきに寄与しません。

`events.negative_signals` を有効にすると、それ以上のことをします。取り消されたアイテムと、そのコンテキストに残っているほかのアイテムとの辺が、`相手のイベントスコア × events.negative_weight` だけ減ります。減少は対称で、バッファにある相手のイベント 1 件ごとに 1 回適用されます。

頼りにする前に知っておくべき性質が 2 つあります。減少は相手のスコアに対して線形ですが、正の共起は 2 つのスコアの積なので、1 回の非表示は辺を削るだけで消し去りはしません。これは補正であって取り消しではありません。もう 1 つは、同じコンテキストと同じアイテムに対する 2 回目の `DEL` は重複として扱われ、そのコンテキストでそのアイテムに再び関与するまで何も変わらないことです。

段階的な手がかりが欲しいなら、低い `ADD` スコアのほうが適していることが多くあります。2 秒で離脱をスコア `5`、完視聴をスコア `95` とすれば、それだけで両者が作るすべての組に 19 倍の差が付きます。

## 繰り返しの関与

既定では、同じコンテキスト・アイテム・スコアの繰り返しは `events.dedup_window_sec` 秒以内なら捨てられます。この既定値はカタログ型のアプリケーションを二重送信から守りますが、同じクリップを 3 回見直すことこそ順位が拾うべき合図であるフィードでは、本物の手がかりを黙って捨てます。

すべての繰り返しを数えるには `events.dedup_window_sec: 0` にします。`events.dedup_cache_size` には触れないでください。`0` にすると重複排除そのものが止まり、負のシグナルが依存している `SET` と `DEL` の冪等性の管理まで無効になります。

## メモリを抑える

途切れない書き込みの流れには、索引の成長を止めるものが何もありません。それを抑えるのが次の 5 つのキーです。

| キー | 抑えるもの |
|---|---|
| `events.ctx_buffer_size` | コンテキストごとに保持するイベント数。リングバッファです。2 つのアイテムが一緒に関与されたとみなす窓幅でもあります。 |
| `events.max_contexts` | 保持するコンテキスト数。最後に使われてから時間が経ったものから捨てられます。`0` は上限なしです。 |
| `events.max_neighbors_per_item` | アイテムごとに残す隣接数。スコアの絶対値で順位づけます。`0` は上限なしです。 |
| `events.min_support` | 辺を消す下限。スコアの絶対値で判定します。`0` で無効です。 |
| `events.dedup_cache_size` | 重複排除の LRU が持つエントリ数。 |

視聴者の数に比例して増えるのは `max_contexts` で、しかも既定では上限がありません。視聴者ごとに 1 コンテキストを持つフィードでは、一度でも観測された視聴者の分だけエントリが溜まります。開いたままにせず、そのプロセスが抱えるべき実働の視聴者数に設定してください。

`min_support` と全体減衰は組で働きます。減衰はタイマーで古い辺をゼロへ押しやり、そこまで来た辺を実際に取り除くのが `min_support` です。`min_support` を既定の `0` のままにすると、減衰した辺は縮むだけで消えず、索引は増える一方になります。

## ひととおり動かす

```yaml
events:
  ctx_buffer_size: 30
  max_contexts: 500000
  max_neighbors_per_item: 200
  min_support: 1.0
  dedup_window_sec: 0
  decay_interval_sec: 900
  decay_alpha: 0.9
  temporal_cooccurrence: true
  temporal_half_life_sec: 3600.0
  negative_signals: true
  negative_weight: 0.5
```

alice が 2 本のクリップを続けて見ます。

```bash
NOW=$(date +%s)
nvecd-cli -p 11017 EVENT u_alice ADD clip_sunset 90 timestamp=$NOW
nvecd-cli -p 11017 EVENT u_alice ADD clip_reef   95 timestamp=$NOW
nvecd-cli -p 11017 SIM clip_sunset 5 using=events
```

```text
(1 results, showing 1)
1) clip_reef (score: 8550)
```

2 つの関与が同じタイムスタンプなので、時間による目減りのない `90 × 95` です。

bob は `clip_sunset` を 1 時間前に、`clip_forest` をたった今見ました。

```bash
nvecd-cli -p 11017 EVENT u_bob ADD clip_sunset 90 timestamp=$((NOW - 3600))
nvecd-cli -p 11017 EVENT u_bob ADD clip_forest 95 timestamp=$NOW
nvecd-cli -p 11017 SIM clip_sunset 5 using=events
```

```text
(2 results, showing 2)
1) clip_reef (score: 8550)
2) clip_forest (score: 4275)
```

積は同じ `90 × 95` ですが、半減期 1 つ分の隔たりで `4275` に半減しています。これが時間減衰の働きそのもので、これがなければ 2 つの組は区別できません。

続いて alice が `clip_reef` を非表示にします。

```bash
nvecd-cli -p 11017 EVENT u_alice DEL clip_reef
nvecd-cli -p 11017 SIM clip_sunset 5 using=events
```

```text
(2 results, showing 2)
1) clip_reef (score: 8505)
2) clip_forest (score: 4275)
```

`clip_sunset` のスコアが `90` だったので、辺は `90 × 0.5 = 45` を失いました。同じ `DEL` を繰り返しても何も変わりません。そのコンテキストとアイテムについて記録済みの状態と照合して重複と判定されるからです。

## 制約

先行書き込みログは既定で無効です。書き込みが絶えず発生するフィードでは、正常でない停止をすると最後のスナップショット以降がすべて失われます。`wal.enabled` を有効にすると、受理したすべての書き込みが応答を返す前にディスクへ載ります。それをどこまでスループットと引き換えにするかは `wal.sync_on_write` と `wal.sync_interval_ms` で決めます。

レプリケーションもシャーディングもありません。1 つのデータセット、1 つのプロセス、1 つのノードです。読み取り専用の複製は、複製元で `DUMP SAVE`、ファイルをコピー、複製先で `DUMP LOAD` という手順を運用側でスクリプトにすれば作れますが、これはある時点のもので継続的な仕組みは背後にありません。保存後に複製元へ届いた書き込みは複製に入りません。

このガイドはスループットも遅延も数値を挙げていません。数値はトラフィックの形と機材で決まるからです。何をどの機材で計測したかは[ベンチマーク](../benchmarks.md)に記録しています。

スコアの計算規則、2 つの減衰、刈り込みの挙動は[イベントと共起](../events-and-co-occurrence.md)で詳しく説明しています。
