# レコメンド

nvecd でいちばん小さくできることです。操作の流れだけからレコメンドを組み立てます。ベクトルも埋め込みモデルも学習の工程も要りません。「このアイテムを扱った人は、ほかに何を扱ったか」に答えます。

## 仕組み

`EVENT` は、あるコンテキストの中で 1 つのアイテムが扱われたことを記録します。同じコンテキストに現れた 2 つのアイテムは共起の隣接関係になり、その強さは 2 つのイベントスコアの積を、その組が現れたコンテキストの分だけ累積した値です。`SIM` はアイテムの隣接を、スコアの高い順に返します。

モデルはこれだけです。索引は 2 つ目のイベントから成立し、学習するものも作り直すものもありません。

## コンテキストキーの選び方

コンテキストはまとまりの単位で、「一緒に」が何を指すかを決めます。任意の文字列なので、アプリケーションが名前を付けられるまとまりならそのまま使えます。

| コンテキストキー | できる結びつき |
|---|---|
| `user_<id>` | 同じ人が最近の履歴の中で扱ったアイテム |
| `session_<id>` | 1 回の訪問の中で扱われたアイテム |
| `order_<id>` | 1 回の取引で購入されたアイテム |
| `playlist_<id>` | 編集者が並べて置いたアイテム |

コンテキストは直近 `events.ctx_buffer_size` 件のイベントをリングバッファに保持し、共起するのはそのバッファに同居しているアイテムだけです。つまりバッファ長が「一緒に」の窓幅そのものになります。バッファ 50 件のユーザー単位コンテキストなら、そのユーザーの直近 50 回の操作とアイテムが結びつきます。注文単位のコンテキストなら、その注文の中身とだけ結びつきます。コンテキストを狭くとるほど結びつきは鋭くなりますが、それだけ多くのイベントが要ります。広くとれば使える関係が早く育ちます。

`events.max_contexts` は保持するコンテキストの上限で、最後に使われてから時間が経ったものから捨てられます。既定値は `0` で、上限なしです。

コンテキストとアイテムの識別子は空にできず、空白文字や制御文字を含められません。`0x80` 以上のバイトはそのまま通るので、UTF-8 の識別子が使えます。

## 操作のスコアづけ

スコアは `[0, 100]` の整数です。組の寄与は 2 つのスコアの積なので、目盛りは線形ではなく二次で効きます。`100` の購入どうしなら辺に `10000` が加わり、`60` の閲覧どうしなら `3600` です。スコア `0` は辺を作りません。

カタログ型のアプリケーションで使える目安です。

| 操作 | スコア |
|---|---|
| 購入 | 100 |
| カート追加 | 85 |
| ほしい物リスト追加 | 70 |
| 商品ページ閲覧 | 60 |
| 一覧での表示 | 40 |

大事なのは絶対値よりも段の間隔です。アプリケーションが望む順位になるように間隔を決めてください。

## ADD・SET・DEL

`EVENT` は 3 つの型のどれかを取り、繰り返しの扱いが違います。

| 型 | 意味 | 繰り返しの扱い |
|---|---|---|
| `ADD` | 流れてくるイベント。クリック、閲覧、購入 | 同じコンテキスト・アイテム・スコアの繰り返しは `events.dedup_window_sec` 以内なら捨てられます |
| `SET` | 状態のイベント。評価、ブックマーク、いいね | 同じコンテキスト・アイテムに同じ値を送り直しても何も起きません |
| `DEL` | 取り消し。いいねの解除、ブックマークの削除 | 要求の内容によらずスコア `0` で記録されるため、結びつきには寄与しません |

クライアントが安全に再送できるのは `SET` のおかげです。`EVENT dave SET widget 90` を 2 回送っても索引の状態は 1 回送ったときと同じなので、タイムアウト後の再送でスコアが膨らむことはありません。

## ひととおり動かす

同梱の設定例でサーバーを起動します。

```bash
./build/bin/nvecd -c examples/config.yaml
```

3 人の買い物客が何をしたかを記録します。買い物客がコンテキストで、購入がイベントです。

```bash
nvecd-cli -p 11017 EVENT alice ADD widget 100
nvecd-cli -p 11017 EVENT alice ADD gasket 80
nvecd-cli -p 11017 EVENT bob   ADD widget 100
nvecd-cli -p 11017 EVENT bob   ADD flange 95
nvecd-cli -p 11017 EVENT carol ADD gasket 80
nvecd-cli -p 11017 EVENT carol ADD flange 95
```

いずれも受理されたコマンド名を返します。

```text
EVENT
```

`widget` と一緒に扱われたものを聞きます。

```bash
nvecd-cli -p 11017 SIM widget 10 using=events
```

```text
(2 results, showing 2)
1) flange (score: 9500)
2) gasket (score: 8000)
```

`flange` が `9500` なのは、bob が `widget` と並べて買ったからです（`100 × 95`）。`gasket` の `8000` は alice の `100 × 80` です。carol の組は `gasket`–`flange` の辺に効いていて、`widget` の隣接には関係しません。

## 結果の読み方

`nvecd-cli` は端末向けに応答を整形します。ワイヤ上の形式は、件数の行に続いて結果 1 件につき 1 行です。

```text
OK RESULTS 2
flange 9500.0000
gasket 8000.0000
```

共起検索のスコアは累積した積そのものです。上限がなく、同じ組が現れ続ける限り伸び、比較できるのは 1 つの結果セットの中だけです。`9500` という値それ自体は何も意味しません。

`using=` を省くと既定の統合検索になります。ストアにベクトルがなければ、統合検索はイベント側の手がかりだけに落ちて、結果セットごとに最小最大正規化で `[0, 1]` に収めます。

```bash
nvecd-cli -p 11017 SIM widget 10
```

```text
(2 results, showing 2)
1) flange (score: 1)
2) gasket (score: 0)
```

順位は同じで、目盛りだけが変わっています。最下位の結果はちょうど 0 に正規化されますが、`min_score` の既定値が `0` で比較が以上判定なので、そのまま返ります。この形のデータでは、共起検索に素の下限を付けるほうが読みやすい絞り込みになります。

```bash
nvecd-cli -p 11017 SIM widget 10 using=events min_score=9000
```

## 古い結びつきを薄れさせる

共起スコアは、重みを取り除く仕組みがなければ際限なく積み上がります。それを担うのが独立した 2 つの機構です。

全体減衰は `events.decay_interval_sec` 秒ごとに索引のすべてのスコアへ `events.decay_alpha` を掛けます。同梱の既定値は 1 時間ごとに `0.99` です。好みが安定している対象には遅い減衰が、入れ替わりの速いカタログには速い減衰が向きます。

刈り込みは、減衰しきって意味を失ったものを取り除きます。`events.min_support` はスコアが下限を割った辺を消し、`events.max_neighbors_per_item` は各アイテムについて強い隣接だけを残します。どちらも既定では無効で、小さなカタログなら困りませんが、大きなカタログでは困ります。書き込みの多いワークロードを一定の範囲に収める設定は[リアルタイムフィードのガイド](./real-time-feed.md)にあります。

## 共起だけではできないこと

誰も触っていないアイテムには隣接がなく、そのアイテムへの検索はエラーではなく空の結果を返します。

```bash
nvecd-cli -p 11017 SIM sprocket 10 using=events
```

```text
(0 results)
```

代わりの手はありません。観測されていないアイテムは、どう調整してもイベントからは推薦できません。これがコールドスタートの限界で、ベクトルを足す理由になります。

イベントだけの構成ではメタデータによる絞り込みも使えません。`METASET` はアイテムにベクトルがあることを前提としていて、なければ失敗します。

```bash
nvecd-cli -p 11017 METASET sprocket category:tools
```

```text
(error) Vector not found for metadata: sprocket
```

メタデータが 1 件もなければ、検索に付けた `filter=` は何にも一致しません。

## ベクトルが効きはじめるところ

上のどちらかの限界が実際のコストになったらベクトルを足します。新規出品が途切れず、操作データが溜まるのを待てないカタログや、カテゴリ・在庫・価格で結果を縛る必要がある場合です。ベクトルを持てば、アイテムは保存された時点から内容で推薦できるようになり、`using=fusion` が検索ごとに 2 つの手がかりを混ぜます。アイテムごとのイベントの量に追随する重みづけも含めて、[EC サイトのガイド](./e-commerce.md)で扱っています。

ベクトルを足しても、ここまでに書いたことは何も変わりません。イベントはそれまでどおりに動き、`using=events` はイベントだけから答え続けます。

スコアの計算規則、減衰、刈り込みは[イベントと共起](../events-and-co-occurrence.md)で詳しく説明しています。
